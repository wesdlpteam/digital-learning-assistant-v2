# DLA Studio sandbox — presentation demo

**Date:** 2026-07-29
**Status:** requirements captured from Nathan, design in progress
**Companion to:** `2026-07-29-dla-sandbox-demo-design.md` (the teacher-facing sandbox, shipped and live at https://wesdlpteam.github.io/dla-sandbox/)

## Purpose

A second unplugged demo page, this time of the curator-facing **DLA Studio**, so the webinar and conference audience can see how the content is managed and what the adoption picture looks like. Same hard constraint as the public sandbox: **no AI calls, no backend calls, no possibility of spend**.

## Where it lives

Same repo as the public sandbox, second page:
`https://wesdlpteam.github.io/dla-sandbox/studio.html`

Generated by the same build script (extended), never hand-edited.

## How the real Studio differs from the public site (and why this is harder)

- The public site is one self-contained `index.html` that reads a static `data.json`. Easy to unplug.
- The Studio is `DLA_Studio.html` plus **nine** classic scripts in `js/` (~880 KB, ~15,000 lines), and it does **not** read a static file. It signs the user in with Google (GIS OAuth, `CLIENT_ID` in `js/00`), holds a `DRIVE_TOKEN`, and pulls `data.json` / `libraries.json` **live from Google Drive**, then writes back through the `gas_backend` `/exec` endpoint (`SCRIPT_URL`, same deployment the public site's AI picker uses).
- `DATA` is declared `let DATA = []` in `js/00`, so like `S`/`CN`/`D` on the public site it is a **global lexical binding, not a `window` property**. Reach it by bare name.

Consequences for the build:
1. Sign-in must be bypassed entirely — the audience has no Wesley account.
2. The Drive load must be replaced with a local prepared JSON file.
3. Every write path must be dead. The runtime guard makes this safe by construction rather than by hunting every call site.

## Approach

Reuse the proven three-layer pattern from the public sandbox:

1. **Runtime guard** (`sandbox-guard.js`, already built and tested) injected before any Studio code. Blocks all cross-origin `fetch` and `sendBeacon`. This is the money guarantee: even a call site nobody found cannot reach OpenAI or Drive.
2. **Anchored transforms** on `DLA_Studio.html` and `js/00` to neuter `SCRIPT_URL`, `CLIENT_ID` and `ANALYTICS_SHEET_ID`, and to inline the js files so the page is self-contained.
3. **Studio shim** injected last: fakes a signed-in session, feeds `DATA` and the libraries from local prepared JSON, freezes analytics, disables write buttons, and applies the content and layout changes below.

## Content changes Nathan asked for

These are demo-presentation changes, applied at build time to the prepared JSON and by the shim. None of them touch live data.

### Data
- **Remove all Kinder year groups** (3 Year Old Kinder, 4 Year Old Kinder). These 23 units — Elsternwick 11, St Kilda 12 — carry no tech ideas at all in the live corpus, so they show as empty and undermine the demo. Removing them takes the demo corpus from 158 units to **135**.
- **Apply the same Kinder removal to the already-live public sandbox**, so the two demos agree and nobody taps Kinder on their phone and finds an empty page.
- **Mark every remaining unit human-verified**, so counts read **135 / 135**.

### Dashboard
- "23 units with no planner" becomes **zero**. No Kinder examples listed.

### Browse tab
- Remove **Inspire all**.
- Remove **Sweep app smashes**.
- Remove **Makerspace reboot**.

### Bulk tab
- Remove the **Audit suggestions** section.
- Remove the **clean up "The Twist" wording** section.

### Tool Inventory
- The whitelist tools list should **fill the full page width** rather than sitting in a narrow column.

### Analytics
- The real sheet shows a quiet week, which reads badly and is not representative — Nathan's account is that historical usage has been strongly positive.
- Build a **frozen sample dataset** representing a strong, realistic week: used across **all three campuses** and all year levels, sessions and time-on-page consistent with the Weekly Scorecard thresholds already in the UI (campus reach 3 of 3, weekly sessions well above the 10+ teacher bar, avg time on page above the 20 s bar, year level coverage complete).

### Buttons
- Every control that would normally generate, save, sync or push is **visible but greyed out**, with a short note that it is turned off in the demo. Not hidden — the audience should see the capability exists.

## Honesty requirement (non-negotiable in this build)

The analytics screens are the one place where a photograph could be mistaken for Wesley's real adoption figures.

- The corner badge (`Sandbox demo — not live data`) appears on every screen, as on the public sandbox.
- **In addition**, the analytics and dashboard screens carry an inline, visible line: **`Sample data — demonstration only`**, placed so it appears in any screenshot of the numbers.

The sample week is modelled on what Nathan reports is historically true, not invented from nothing, and it is labelled as sample data wherever it appears. That combination is what makes presenting it honest.

## Success criteria

1. Loading `studio.html` and clicking through every tab produces **zero** requests to `script.google.com`, `googleapis.com` or `accounts.google.com`.
2. No sign-in prompt appears; the page lands straight on the dashboard.
3. Unit counts read 135 / 135 everywhere; no Kinder year group appears anywhere.
4. Dashboard shows zero units without a planner.
5. The named Browse and Bulk sections are absent; the whitelist fills the page width.
6. Analytics shows the strong sample week across all three campuses, with `Sample data — demonstration only` visible on screen.
7. Every generate/save/sync control is present but disabled with a note.
8. The live Studio, live data, and both backends are byte-for-byte unchanged.
9. The public sandbox is rebuilt without Kinder and redeployed.

## Non-goals

- No real sign-in, no Drive access, no write path of any kind.
- No attempt to make disabled buttons simulate their work.
- No changes to the real Studio's behaviour for Wesley staff.
